# ADR 0003: Measure before rewriting the worker in Rust

Status: retain the Python controller/worker for current language delivery; revisit a Rust worker using measured bottlenecks. Rust target debugging remains a required MVP language regardless of the implementation language of Peeky itself.

The user proposed porting Peeky to Rust for execution speed. Current local evidence does not justify a full rewrite. The Python runtime loop spends most time starting/waiting for the external debugger and target; the reasoning model and compiled build also run outside the Python controller. A faster control language cannot eliminate those costs. Python already delegates digest computation to native implementations, so counting Python source lines does not identify the cost of provenance checks.

The 2026-10-14 HTTP benchmark measured ten fresh runs for each runtime on the same macOS ARM64 host. Python median inspection/mutation were 2.582/1.253 ms and total cycle 993.433 ms. Java median inspection/mutation were 21.743/31.109 ms; launch including fresh javac compilation took 528.074 ms of a 606.110 ms total. Java includes additional source/artifact/adapter integrity checks and differs from Python; these measurements are not a controlled language comparison. Raw samples and reproduction are in PERFORMANCE.md.

Prioritize profiling operation time, hash/inventory work, process startup, memory, remote round trips, and model latency. Keep correctness checks enabled. First remove unnecessary repeated work and measure the result against the same conformance suite. Do not weaken integrity checks or skip termination/cleanup to improve latency. Memory footprint and high-concurrency behavior have not yet been measured, so no claim about Rust's benefit for them is established.

A bounded Rust worker spike is justified when profiling attributes a material share of the user-visible budget to Python CPU/memory overhead, or a deployment needs a measured footprint/startup target Python cannot meet. Compare both implementations with the same real-debugger failure tests, source/build provenance checks, latency distribution, peak memory and packaging costs. Require an end-to-end improvement large enough to justify maintaining or replacing the implementation, with thresholds selected for the actual workload. Keep the HTTP contract and adapter boundaries stable so a native worker can be evaluated independently of the agent/controller.

## 2026-10-16 measurement

[PERFORMANCE.md](../PERFORMANCE.md#where-a-probes-time-goes-2026-10-16) attributes probe time to Peeky CPU, child processes and waiting. The largest Peeky-owned cost was repeated work, not Python's speed. Provenance checks rehashed unchanged toolchain binaries (clang is 125 MB) on every operation, using native SHA-256 code that a Rust implementation would have shared. Reusing a digest while a file's device, inode, size, mtime and ctime are unchanged and settled (`src/peeky/digest.py`) made C++ probes 3.1× faster and removed 57 ms from each C++ debugger operation, with every check still running. After the fix, Peeky's own CPU is about 0.5% of a Python probe and 10–15% of a compiled one, so the condition above for a Rust worker spike is still not met.
