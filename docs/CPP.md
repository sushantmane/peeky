# Experimental C++ conformance

Peeky's fixed native target accepts `language: "cpp"` and compiles `.cpp`, `.cc`, or `.cxx` sources with an explicit C++ compiler. The fixture qualifies C++17 builds with debug information, a class object, a reference to that object, `std::array<int, 128>`, and an ordinary local integer. It uses the same source/build identity guards and temporary build lifecycle as C.

**Compiler: clang only** (#167). Peeky's C++ rules (declared-below, unset by an initializer, previews, map lookups, libstdc++ strings, string sets, same-named locals) were checked against clang's debug information only, and the build passes clang's `--driver-mode=g++` (the resolved `clang++` is `clang`, which picks its language from its name). Before a C++ build, Peeky runs the configured compiler's `--version` once per compiler file (path, modification time and size) and refuses any compiler that does not say `clang version`, before anything is built: `UNSUPPORTED: C++ targets need clang++ (Peeky's C++ rules are checked against clang's debug info); set PEEKY_NATIVE_CXX to clang++ (/usr/bin/aarch64-linux-gnu-g++-13 is GCC)`. It goes by what the compiler says, never by its name: macOS's `g++` is Apple clang and is accepted. A compiler-masquerading wrapper (a `ccache` or `distcc` symlink named `clang++`) is refused, because its own `--version` is not clang's; a wrapper script that runs clang++ (`exec ccache clang++ "$@"`) passes clang's `--version` through and works. A compiler that does not answer `--version` within 10 s is refused as timed out, and it and every process it started in its process group are ended. C targets build with clang or GCC.

`examples/cpp/pagination_bug.cpp` intentionally calculates the first item with `page * page_size`. At the `OBSERVE` line, the default first page has `start == 3`. Changing this local integer to `0` tests the pagination hypothesis without changing the source or rebuilding the running executable. The deterministic agent test then rejects a compilation error and an overfit `start = 0` patch before accepting `(request.page - 1) * request.page_size` against an independent checker. That checker starts fresh processes for 12 valid cases and 10 invalid argument cases. Numeric inputs are parsed with `strtol` and bounded before arithmetic.

The agent test uses separate identical controller/worker source directories on the same host and the authenticated HTTP interface. Decision fixtures replace the model call in required CI. This demonstrates path independence, not separate-host deployment.

A trusted configuration for the fixture, with the worker root set to `examples/cpp`, is:

```json
{
  "language": "cpp",
  "sources": ["pagination_bug.cpp"],
  "headers": ["pagination.hpp"],
  "compiler": "/usr/bin/clang++-18",
  "adapter": "/usr/bin/lldb-dap-18",
  "dwarfdump": "/usr/bin/llvm-dwarfdump-18"
}
```

Pass the saved configuration to `peeky-worker --native-config config.json` or `peeky-agent --native-config config.json --program pagination_bug.cpp --check verify_pagination.py`. Supply the existing `DEBUG_TOKEN` requirement and the intended `--root`. On macOS also configure `dsymutil` and the SDK `sysroot`, with compiler/debugger paths returned by `xcrun --find`.

Local conformance runs use:

```sh
PEEKY_NATIVE_DAP="$(xcrun --find lldb-dap)" \
PEEKY_NATIVE_CXX="$(xcrun --find clang++)" \
PEEKY_NATIVE_DWARFDUMP="$(xcrun --find llvm-dwarfdump)" \
PEEKY_NATIVE_DSYMUTIL="$(xcrun --find dsymutil)" \
PEEKY_NATIVE_SYSROOT="$(xcrun --show-sdk-path)" \
pytest tests/cpp --durations=10
```

The independent Ubuntu 24.04 CI lane acquires LLVM 18 from signed Ubuntu package repositories, records installed package revisions, and has a four-minute timeout. It has no dependency on the C or Java lanes. The budget is a target; measured hosted results determine whether it is met.

This slice does not qualify arbitrary STL visualizers, overloaded operators, expression evaluation, pointer/reference reassignment, class mutation, or C++ build systems. Optimized builds are opt-in, with locals reported as `unavailable` when they have no value (see NATIVE.md). Mutations remain restricted to supported integer locals and their integer fields and fixed-size array elements, reached without a pointer or reference and outside unions, packed and `std::` types (#105; see NATIVE.md). Debugger display types and standard-library storage member names differ between platforms; conformance must check actual values without assuming libc++ and libstdc++ have identical layouts.

Read-only `expand` accepts a variable's opaque `variablesReference` as `handle`, together with the current session/stop, `start`, and `count` (at most 64), and `previews` (true to preview the values it lists, #136; `inspect` takes `previews` too: true, the default, false, or the roots to preview). Read-only `preview` gives one value's preview by its `handle` (`pointee`: true for what a pointer points at), or nothing. Collections are bounded internally to 512 entries, with depth and inspection-node limits. Expansion revalidates the source/build, frame, scope, and child ancestry. Any expansion revokes mutable scope handles; inspect again before mutating a scalar. A fresh inspection invalidates earlier child handles as well.

On the locally tested Apple LLDB 21, both the `Pagination` object and `Pagination &` reference expand to `page`, `page_size`, and `total`. The `std::array` exposes a raw `__elems_` storage child, which expands to integer elements. The test accepts the corresponding single raw storage member on other standard libraries or direct indexed elements, while requiring the first three values to be 10, 20, and 30. Hosted LLVM 18 qualification remains a separate CI result rather than an assumption about its display shape.

## Maps and sets (#119)

LLDB lists the entries of `std::map`, `std::unordered_map`, `std::set`, `std::multimap` and the other associative containers as `[0]`, `[1]`, ... in iteration order, in libc++ (macOS) and libstdc++ (Linux) alike, with only the entry's type (`std::pair<const int, int>`) to tell them from a vector's elements. In C++, `m[1]` on a map is the value for key 1, so reading the debugger's `[1]` showed a wrong value with no note: for `std::map<int, int> m{{2, 20}, {1, 10}, {5, 50}}`, `m[1].second` read `20`. Selectors on these containers now never take a position for a key:

- `m[K]` on a map with unique keys (`std::map`, `std::unordered_map`) is the value for key K, as C++'s `m[K]` is: the `second` of the one entry whose `first` the debugger shows as exactly K. Integer keys (`short` to `long long`, signed or unsigned, under their LLDB or GCC names) match the selector's integer, which must be in the key type's range; `std::string` keys match a quoted selector (`m["al"]` or `m['al']`) of printable ASCII without `"` or `\`, against the debugger's `"al"`. A missing key is `not found`, with the keys there are (in C++, `m[K]` would insert it). Keys of any other type (floating point, `char`, `bool`, enums, classes, `const char *`, which C++ compares by address) and selectors of the other kind are refused, with how to select the entry instead.
- A `std::string` key matches only a string of its length. LLDB prints a libc++ string from its size, a NUL as `\0` (`SetBinaryZeroIsTerminator(false)` in LLDB's `LibCxx.cpp`), so its summary is the whole string; libstdc++'s summary is the `_M_dataplus._M_p` C string, which ends at the first NUL (`"a\0b"` shows as `"a"`). The worker says which a build has (`whole_string_summaries`, from `std::__1` and `std::__cxx11` in the debug information); for libstdc++ it checks every string against its `_M_string_length` (see Strings, #128), and a key matches only a string shown whole and of its length (`string_length`), or read from memory.
- Absence is claimed (`not found ... would insert it`) only where C++'s `m[K]` could find no other key: a `std::map` with `std::less` or `std::greater`, a `std::unordered_map` with `std::hash` and `std::equal_to`. With a comparison of the map's own (`ByAbs`, a case-insensitive `NoCase`, `LowerHash`/`LowerEq`), an exact key reads, and otherwise the error says no key equals K exactly and that the map may treat another as equal; bisection runs only under `std::less` and `std::greater`.
- `m[#N]` is the Nth entry in iteration order (a map's pair, with `.first` and `.second`, or a set's element). It is accepted only on these containers; elsewhere `[N]` indexes.
- Sets, multisets and multimaps (also unordered) have no `[]` in C++, so `s[N]` and `mm[N]` are refused, naming `s[#N]`.
- `session get m` lists a map's entries as `m[K]: V = value` when its keys compare (the selector reads what the row shows), and every other container's as `m[#N]`, with a note saying which. A key no selector can write (over six digits, a string that is not plain) is listed by position, and two entries never share a label. A pointer's entries are `p[0][K]` (#102), and `p[1]` is refused with `p[0][1]`, the value for key 1.
- The container is told by its type as LLDB shows it (`std::map<…>`, `std::__1::map<…>`, `std::__debug::map<…>`, `std::pmr::map<…>`, through `const` and `&`), or, for a typedef, by the class the build's debug information gives it (`typedef_kinds` records it; the worker adds `aliased_type`), also behind a reference (`const Index &`) or a pointer (`IntSet *`, `pointee_aliased_type`). A class's member typedef (`Holder<std::string>::S`, which lldb-dap and the debug information spell differently) keeps the class every instance's typedef names, or the map or set template they all instantiate (`std::map`); where they disagree and one is a map or set, the type is `?`, and `t[N]` is refused (`t[#N]` reads by position). A typedef the debug information does not resolve, whose children the debugger lists as pairs with a const key, may be a map or a vector of such pairs: there `t[N]` is refused and `t[#N]` reads by position.
- A `std::map` with integer keys and the standard order (`std::less`, which LLDB leaves out of the type's name, or `std::greater`) and more than 20 entries is bisected, reading about log2(size) entries; its size is the summary's `size=N`, checked against the listing. Any other map is read entry by entry, one node per entry and one per key, within the inspection's 512 nodes: a map too big for that is refused before any entry is read. A listing shorter than the summary's size never says a key is absent.

Known gaps: floating-point, `char` and other keys read only by position; a typedef the debug information does not resolve at all (no class for its name) is told from a vector only by its entries, so a set behind one reads `s[N]` by position as a vector would; `std::flat_map` and `std::flat_set` (C++23) are recognized by name but not qualified with a real build. Rust's `HashMap` and `BTreeMap` are not affected: Peeky does not load Rust's LLDB formatters, so LLDB shows their raw fields and `m[1]` finds no element.

## Strings (#128)

LLDB's summary of a libstdc++ `std::string` is the `_M_dataplus._M_p` C string (`LibStdcppStringSummaryProvider` sets `SetBinaryZeroIsTerminator(true)`), so `"a\0b"` showed as `"a"`, with no note, wherever the value appeared. A value LLDB names `std::string` gets the summary string `${var._M_dataplus._M_p}` instead, which fails on clang's Linux builds (it leaves `_Alloc_hider` incomplete, expecting libstdc++'s own debug information): `error: summary string parsing error` was shown as the value. LLDB prints a libc++ string from its size, every byte (a NUL as `\0`), so on macOS nothing changes.

For libstdc++ (`whole_string_summaries` false), the worker's `string_value` hook (`peeky.cxx_strings`) reads each `std::basic_string`'s members through the debugger's own reference (any depth; one value-view read, within the inspection's view budget) and compares the summary's length, counted as LLDB escapes it, with `_M_string_length`. A string is known by its type's name (`std::string`, `std::basic_string<char>`, `std::__cxx11::basic_string<char, …>`, by value, reference or pointer), by the class a typedef of it names in the build's debug information (`typedef std::basic_string<char> Bytes`, `using Name = std::string`, `const Name &`, `Bytes *`, a template's member typedef; see `aliased_type`, #119), and, under any other name, by its members: a value LLDB shows as a literal (or as a failed summary), other than C's own `char *`/`char[N]`, whose `_M_dataplus` is a `std::basic_string<C>::_Alloc_hider` (which names the character type) beside a `_M_string_length`. LLDB applies its libstdc++ formatters to a typedef's canonical class, so `Bytes b` showed `"b"` for `"b\0y"`, and `Name tn` the parsing error, with no note (review of #131):

- Equal (or a `char` summary cut at LLDB's 1024 bytes, marked `...`, with no NUL before): the debugger's text stays, marked `string_length` for map keys (#119).
- Otherwise, with `readMemory` (lldb-dap 20): the data pointer and length are read from the string's first two words (the length checked against `_M_string_length`), then up to 1024 characters (one 32-byte request for a string in its own 16-byte buffer, a second for one on the heap), shown as LLDB's libc++ summary shows them (`\0`, `\t`, `\"`, `\U0000001b` for a control character, `\xff` for a byte that starts no UTF-8 sequence, `"..."...` past the bound), with `view: memory`. `std::wstring` (`L"…"`, UTF-32), `std::u16string` (`u"…"`) and `std::u32string` (`U"…"`) too.
- Without it (lldb-dap 18): `"v" (shown up to a NUL at byte 1 of 3)`; a failed summary has no value, with its length in the reason (`0x… <no text: …>` after a pointer's or reference's address).
- No `_M_string_length` in view (clang leaves `std::wstring`'s members to libstdc++'s debug information; libstdc++'s old ABI): `(not checked for a NUL byte: …)`, or no value where the summary failed.

Every string literal is then spelled so that C reads it back as the same bytes (`tidy`): LLDB writes a NUL as `\0` and an invalid byte as `\xff` even before a digit, so the bytes n, NUL, `6`, `4` showed `"n\064"`, which C reads as `"n4"`, and `\xff` then `a` showed `"\xffa"`, one character to C. There, and only there, the three-digit octal form is used: `"n\00064"`, `"x\0005"`, `"\377a"`; everywhere else the text is LLDB's libc++ spelling, unchanged (`"a\0b"`, `"\08"`). This applies to LLDB's own libc++ text on macOS too: re-reading memory there would cost a request per string to fix a spelling, while LLDB's escapes are unambiguous to Peeky, which counts them as LLDB writes them (`\0` is always one NUL; LLDB never writes other octal escapes) and respells only the debugger's own text, once (a literal Peeky read from memory is spelled as C reads it already, and Rust's `\0` is never followed by more digits, so Rust literals stay as LLDB shows them). A literal is kept within the worker's 2000 characters (with its address and note), cut between characters with LLDB's `...`: a noted value was 5041 characters, and a long libc++ text was cut inside an escape with no mark.

LLDB's `error: summary string parsing error` (also `error: no target`, `error: no ScriptInterpreter`) is never shown as a value, for any C or C++ type, string or not, nor saved as one: a value with only that text is unavailable (`LLDB's summary of this value failed (...); select its members`), and after a pointer's address it reads `0x… <no text: …>`.

Cost on libstdc++: one `variables` request per string (its members), and, where the summary is cut or failed and the debugger reads memory, one or two `readMemory` requests. LLDB's text gives no sign of a NUL it dropped, so every string is checked; the requests count against the inspection's view budget (128 per inspection or expansion, 10 s), so a page of a large `std::vector<std::string>` can end with strings marked `(not checked for a NUL byte: …)` rather than vouched for. libc++ (macOS) costs nothing.

`--set` changes a `std::string` local to a text in double quotes since #137 part 2 ([C and C++ cookbook 7.1, Changing Text](lang/c-cpp-cookbook.md#changing-text)): in place, within its capacity, where the layout read from its members agrees with memory. Qualified by real builds in `tests/cpp/test_cpp_strings.py` with lldb-dap 18 and 20 (the Docker `cpp-llvm20` lane sets `PEEKY_EXPECT_READ_MEMORY`). Known gaps: with lldb-dap 18, a `std::string` value (and one under a typedef of that name) has no text at all (its summary fails), and an incomplete `std::wstring` has none with either; a string inside another value's own summary would not be rewritten (vectors, maps and structs show none); a `const char *` stays a C string, as C has it; `std::string_view` is not covered.

## Structured bindings of a reference are never changed (#186 review)

`auto &[at, dropped] = *owner;` gives `dropped` and `at` no storage of their own: clang describes each as a variable of the member's type at a location read through the hidden reference (`DW_OP_fbreg -16, DW_OP_deref, DW_OP_plus_uconst 0x18`), which `fields.local_types` called the frame's own (`automatic`). `dropped` showed `[settable]`, and `--set dropped=50` wrote `o.dropped` in the caller through the reference. A variable whose location reads through a pointer is now stored as `through`: as a root it is never marked and `--set` refuses it (`` `dropped` is reached through a pointer or reference …: Peeky changes only values the frame holds itself and does not write through a pointer or reference ``), at the stop and, where the build shows it in every function at the `--at` line, before the program runs; its fields show `[not settable: reference]` and are refused alike. The same holds for a named return value (whose object is the caller's) and, in C on macOS, a `__block` variable. A by-value structured binding (`auto [a, b] = pt;`, a constant offset in the frame) and a by-value parameter the ABI passes through a hidden pointer (a struct over 16 bytes on arm64, any class with a destructor: the call's own copy) change as before. GCC's variable-length arrays are read through a pointer too; their elements are refused as such. Qualified by `tests/cpp/test_cpp_bindings.py` and `test_a_c_local_reached_through_a_pointer_is_never_changed` (macOS).

## Strings, frame names and block spans (sixth evaluation)

**A string lists no members** (finding 15). `session get name` for a libc++ `std::string` listed `[not selectable]: std::basic_string<char>::(anonymous struct) = … @ 0x16b24f238` under its text, and libstdc++'s lists `_M_dataplus` (whose `_M_p` is the C string LLDB cuts at a NUL), `_M_string_length` and an unnamed union. `NativeSession.string_value` now marks a standard string `text` when the value shown is its text, or Peeky's reason it has none: by its type's name or a typedef's class (libc++ and libstdc++), or, on libstdc++, by its members (#128); never a value LLDB shows without text (`std::u16string @ 0x…` with lldb-dap 18), whose members stay. The worker gives such a value no handle, as Rust's text views have none: `inspect` offers no `(children: …)`, `get` lists no rows, a struct's, vector's or map's listing marks its strings not expandable, and the depth limit never applies. Selecting into one (`name[0]`, `name.size`, `ref.x`) is refused, saying to capture the string and compare its text. A pointer to a string keeps its address and text (`0x… "apple"`); `p[0]` is the string (`_resolve`), `p[1]` is refused as for any pointer. Map keys need no member: the worker's `string_length` (or `view: memory`) carries what `_string_bytes` read from `_M_string_length` (#119).

**Frame names** (finding 16). LLDB names a C++ frame by its demangled signature: `trim_left(std::__1::basic_string<char, std::__1::char_traits<char>, std::__1::allocator<char>> const&)`, about 100 characters, and the probe table about 200 columns. `names.short_function` drops the parameters, qualifiers (`const`, `&`) and a template's return type (`int same<int>(int)` → `same<int>`), keeping the qualified name, template arguments and operators (`main::$_0::operator()`, `Foo::operator bool`, `(anonymous namespace)::helper`); a Java frame (`Main.run(int)`) keeps its own. `function_labels` gives a table's column: the short name, or, for two frames that would read alike (overloads stopped at one line), the signature as `display_function` shows it, else the whole name. `display_function`, used by session text (`stopped at … in trim_left(std::string const&)`, frame listings), keeps the parameters and writes the standard library's types as code does: inline namespaces (`std::__1`, `std::__cxx11`) dropped, `std::basic_string<char, …>` as `std::string` (also `wstring`, `u16string`, `u32string`, `string_view`, the streams), and default template arguments (`std::allocator`, `std::less`, `std::hash`, `std::equal_to`, `std::default_delete`) left out where they are the defaults. A name whose brackets do not balance is left as written. JSON, the evidence store and SQL comparisons keep LLDB's whole name; a probe's or query's text table that shows another name says so in a note (`names.shortened_note`), whose example is the SQL function `short_function(function)`'s value. That function drops every overload's parameters, so overloads share its value (`operator+`, `G::get` for `get() &` and `get() &&`), as do a Rust function's closures and a generic's instances (`captures.instance` tells those apart), and a `GROUP BY` or join on it combines them; a table keeps their parameters where they would read alike, so its label is not always `short_function`'s. Sessions show the signature (parameters kept) and save nothing to the store.

**Block spans** (finding 17). `describe` gave `colon (size_t, lines 17-35)` and `name (lines 22-35)` for a `while` body's and an `if` block's locals in a function ending at line 35. clang's lexical blocks were right; their code was not contiguous: the landing pads that destroy a block's objects when an exception leaves it (`name`, the `substr` temporaries) are inside the block's `DW_AT_ranges` and carry the function's closing line (two rows at line 35 in the `if` block of the evaluation's case; LLDB places line-35 breakpoint locations there, among the function's own), and a span was the lowest and highest of the block's lines. `_block_spans` now splits a block's lines only where a line between two of them runs code none of which is the block's (`_runs`): `name (lines 22-25, 35)`, `colon (lines 17-26, 35)`. A later span starts right after the last such line, since LLDB moves a breakpoint on a line without code to the next line with code, which is then the block's. Lines without code inside a span are kept, and no line the block's code runs on is dropped, so a span is never narrower than where the debugger can show the local; the closing line is listed because a stop there while an exception unwinds sees the block's locals. C's blocks, which have no cleanups, read as before; a Rust `for` loop's variable whose body expands a macro defined above it reads `i (lines 66, 70-71)` (the expansion's line, then the body's from `let s = twice!(i);`, whose code is the macro's), since the loop header's line between them runs outside its block.

Qualified by real builds in `tests/cpp/test_cpp_eval6.py` (the evaluation's `stock.cpp`, strings by value, reference, pointer, typedef, in a struct, vector and map, and overloads on one line), on macOS (libc++) and Linux (libstdc++, lldb-dap 18 and 20). Known gaps: a libc++ string under a type name Peeky cannot resolve (a template's member typedef the debug information does not give) still lists its `(anonymous struct)`; other nameless children (a union inside a struct) are still listed as `[not selectable]`; frame names of other standard templates keep their default arguments.

## Struct and class previews (#136)

C++ classes, structs and fixed-size arrays preview as C's do (NATIVE.md): `{x = 1, y = 2}`, `[{x = 1, y = 1}, …]`. What C++ adds:

- **Base classes** show as LLDB lists them, a member named by its class: `{Base = {b = 1}, d = 2}`. The vtable pointer is not a member of the program's and is left out (`_vptr$Base`, GCC's `_vptr.Base`; the lldb-dap builds tested, 18, 20 and Xcode's, list none).
- **Anonymous members:** an anonymous struct's members show in braces with no name (`{kind = 1, <union>, {u = 5, v = 6}}`); an anonymous union shows `<union>`. lldb-dap 18 names them `<null>`, 20 and later "".
- **References:** a reference local or parameter to a class shows its address, then the preview (`0x… {lo = {x = 0, y = 0}, hi = {x = 2, y = 3}}`), as a `const std::string &` shows its text; a reference to a union or a `std::` type does not. A reference member shows its address only.
- **Standard-library types** keep their own views (#119, #128): a `std::string` shows its checked text (libstdc++ with lldb-dap 18: `<no value>` inside a preview, as the member's own row says why), a standard container its elements (below, #181), and any other `std::` value its debugger's summary or `{…}`. A map's value of a user class (`mp[1]`) is previewed.
- A `union` by any name the debug information gives (a `typedef`, a class's member) is never previewed.
- Types come from the debug information, not lldb-dap's names: `Hold<int[1]> hs[5]` previews its five elements (the name's first `[1]` is a template argument), `char16_t`/`char32_t`/`wchar_t` arrays show element by element (`[u'x', u'\0', u'y']`), and a value reached through a standard container's children (`mp[1]`, `vp[0]`) is typed by the container's template arguments (#181); a map's entry (`mp[#0]`, a `std::pair`) and what other library types hold are not previewed. Optimized builds show no previews (NATIVE.md). A `char16_t`, `char32_t` or `wchar_t` bitfield has no value (LLDB reads its bits wrongly), and a member named as a base class (`struct B2 : A2 { int A2; }`) leaves its class unpreviewed.

Qualified by real builds in `tests/cpp/test_cpp_previews.py` (and the C ones in `tests/native/test_native_previews.py`), on macOS (libc++) and Linux (libstdc++, lldb-dap 18 and 20).

## Standard container previews (#181)

A probe row, `inspect` and `session get` show a standard container's size and first elements, as Java's `ArrayList` and Rust's `Vec` show theirs. In the eighth evaluation's `router` case, `have` (`std::vector<std::string>`) showed only `size=3`; the bug's evidence, `have[2] = ""`, took a session. It now reads `size=3 ["users", "42", ""]`.

- **Forms:** a `std::vector`, `std::array`, `std::deque` or `std::list` is `size=N [e0, e1, …]`; a `std::map` or `std::unordered_map` `size=N {k0: v0, …}`, in iteration order; a set (`std::set`, `std::multiset`, `std::unordered_set`, `std::unordered_multiset`) `size=N {e0, …}`. A `std::multimap` keeps its summary: its keys repeat. Bounds are the struct previews': 8 elements, then `…`, two levels (a vector of structs inside a struct shows `[{…}, {…}]`), 40 characters of one element, 240 in all.
- **Typed by the debug information:** the class template's arguments (`DW_TAG_template_type_parameter`: `_Tp`, `_Key`) give each element's type, which `fields.type_graph` now records and walks for these containers (their storage is behind pointers, so the walk never reached their elements before). An element shows as that type does: a struct as a preview, a pointer as its address, a `std::string` as its checked text (#128), a nested container as its own preview.
- **Read safely:** the elements are the debugger's children, which its formatter (libc++'s and libstdc++'s, in every lldb-dap tested) reads from the container's own storage, `size()` of them: [0], [1], ... matching its `size=N` summary. A container the debugger lists any other way (its own members, as an LLDB without the formatter does; fewer elements than its size) keeps its summary. A `std::array`, which LLDB lists by its one member (`__elems_`, `_M_elems`), shows that C array's elements once the debug information says it holds `_Size` of `_Tp`.
- **Withheld:** a container not yet constructed is `no value yet` (#121, #140), and an optimized build shows only the summary (#136). A moved-from container shows what it holds: libc++ and libstdc++ both leave it empty (`size=0 []`), as `size()` says. A container a standard-library call or a lifetime under way may be changing shows its summary alone, and its elements no preview of their own (a struct element `Noisy @ 0x…`): in a program running more than one thread (a stop pauses the others wherever they are, perhaps inside a `push_back` on a container the stopped thread shares); in a frame below a library function (`main`'s `o.items` while `clear()` runs an element's destructor, the vector still counting an element already destroyed, whose string's memory is freed) or below a constructor, destructor or assignment operator of any class (`slot->~E(); ::new (slot) E(3);` in `main`, stopped in `E::~E()`, left `v` holding an element whose lifetime had ended); and, reached through a pointer or reference (a reference parameter, `this.owner[0].items`), as a static local, or as a local the frame reaches through a pointer, wherever the stack holds such a frame (a `std::thread`'s or `std::function`'s too, or the frame's own constructor or destructor) or where Peeky cannot read it whole (1,024 frames or more, or a `stackTrace` reply short of its `totalFrames`); in each case its elements and everything read through them are withheld too (#187, below). A library frame is one whose name, before its parameters, is in `std::`, `__gnu_cxx::` or `__gnu_debug::`, or one with no name; a constructor is told by the debug information or the name, a destructor or assignment operator by the name (`E::~E()`, `E::operator=(E const&)`).
- **Threads, for sure:** the program runs one thread only where every source agrees: two `threads` replies (lldb-dap answers its first with the threads the program had at launch), LLDB's own `thread list` (asked with lldb-dap's command escape), and every `thread` event that said a thread started since launch (two started threads mean several, for good). The thread IDs of all of them together must be one; a source that does not answer, or a thread without an ID, leaves it unsure, and unsure withholds.
- **Locals reached through a pointer:** clang types a structured binding of a reference (`auto &[items, dropped] = *owner`) as the vector itself, at a location read through the hidden reference (`DW_OP_fbreg -24, DW_OP_deref`), so its storage class said it was the frame's own. Any local whose location is not one frame offset (`fields.referred_locals`: a structured binding of a reference, a class passed by value through a hidden pointer, a named return value) now counts as reached through a pointer.
- **Selectors are unchanged:** `have[2]`, `m[1]` (key 1, #119), `s[#0]`. A map's listing (`session get m`) shows its values' previews (`named["a"]: Pt = {x = 1, y = 2}`).

Qualified by real builds in `tests/cpp/test_cpp_containers.py` (vectors of strings, structs, `bool` and vectors, a moved-from vector, `std::array`, maps, sets, `std::deque`, `std::list`, a struct holding a vector, a reference, a pointer, a caller frame, a destructor during `clear()`, a structured binding of a reference, an element destroyed in place, a second thread (also one held inside `emplace_back`'s relocation), a loop's next pass and an optimized build), on macOS (libc++) and Linux (libstdc++, lldb-dap 18 and 20). Known gaps: a container nested four levels below a local (`grid.idx[1]`) is past the inspection's depth and shows its summary; `std::forward_list`, `std::multimap`, the container adaptors (`std::stack`, `std::queue`) and `std::pair`/`std::tuple` keep the debugger's views.

**Rows read through a container a library call is changing (#187).** In that same state, `main`'s `o.items[1].name` read the freed string of an element `clear()` had destroyed (`"\U00000003\0\0…"`), with no note, and `items[1].name` read it too through the reference parameter of a function the destructor calls. Every row read through a standard container's element (`o.items[1]`, `o.items[1].name`, a map's entry and its `first` and `second`, `items[1]` through a reference) is now withheld under #181's rule above: a program running more than one thread (or one whose threads Peeky cannot count for sure), a standard-library call or a lifetime under way (a constructor, destructor or assignment operator) below the container's frame, or one on the stack for a container reached through a pointer or reference. The row says "not shown: a standard-library call below this frame (std::__1::vector<…>::clear) may be part-way through changing `o.items`, which this is read through (…); read it after that call returns", or, through a pointer or reference, "… while a standard-library call runs on this thread (…)"; a lifetime names "a constructor, destructor or assignment operator" instead. Such a row has no handle, so a selector below it is refused with the same reason, and a map's key lookup says it (`cannot read the keys of o.tags's entries: not shown: …`). The type walk finds the container from the build's debug information (#181), also behind a reference or pointer to it. Which container a library call changes is not told, so every container the frame reads that way is withheld; the container's own row keeps its summary, and values read otherwise (`o.dropped`) are unchanged. With several threads the row says "the program runs 2 threads: a stop pauses every other one wherever it is, perhaps part-way through changing `shared` …" (`shared[0].x` read the moved-from `-1` while a worker thread relocated it). Withholding takes the frames the stop lists, and up to 1,024 of them where a container is reached through a pointer or reference; a reply of as many frames as asked for, or fewer than its `totalFrames`, is not the whole stack, so such rows are withheld. A row's check runs before anything else about it, a name or type too long to show whole included. Qualified by `test_rows_read_through_a_container_a_library_call_is_changing_are_withheld` and `test_rows_read_through_a_container_whose_element_is_destroyed_in_place_are_withheld`, on macOS and Linux.
