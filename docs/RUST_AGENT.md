# Experimental Rust investigation loop

The Rust controller uses the same observation, intervention and candidate-verification flow as Java, C and C++. A fixed Rust worker builds and debugs one dependency-free Cargo binary through LLDB-DAP (see [RUST_GATE.md](RUST_GATE.md)). `RustVerification` rebuilds each candidate in a fresh workspace. Only declared application `.rs` sources are editable; `Cargo.toml`, `Cargo.lock` and the integration-test file are frozen inputs included in every identity check.

## Two independent gates

A Rust candidate passes only when both of these pass on the same fresh build:

1. **Compiled Cargo test.** Preparation runs `cargo build --offline --locked --bin <name>`, then `cargo test --no-run --offline --locked --test <name>` with the same controlled environment. The test executable is selected from the hashed `target/debug/deps` directory: exactly one, matching the declared test name, with no unexpected artifacts. Verification **executes that hashed binary directly** with `--test-threads=1`. Cargo is never invoked at verification time, so nothing can be rebuilt or substituted. Cargo's uplifted `target/debug/<bin>`, which the test runs through `CARGO_BIN_EXE_*`, is a hashed artifact and must be byte-identical to the debugged executable before and after the run. The test runs with a 16,000-byte output limit, so any output beyond the retained capture is an explicit failure rather than silent truncation. The final non-empty line must be the harness's single `test result: ok.` summary, with at least one passing test and zero failed, ignored, measured or filtered tests; the exit code must be zero and the run must not time out. Anything else is a test failure, and an earlier forged summary cannot satisfy this check.
2. **Independent checker.** The unchanged supplied `examples/rust/verify_pagination.py` runs against the prepared descriptor (12 page cases and 10 invalid-argument cases) and must complete through the trusted wrapper. A passing Cargo test can never replace it.

Baseline test failure is recorded and does not stop the investigation; the checker must fail on the original. A failed test assertion or checker case is a verification failure that returns to the decision loop. Candidate compile errors are retryable `build` results only when Cargo's JSON messages (`--message-format=json-diagnostic-short`) show every rustc `error` with a primary span in a declared application source. Span-less errors such as linker or driver failures, errors elsewhere, and malformed or possibly truncated messages are fatal. A test-target compile failure, toolchain/probe failure, unexpected artifact, executable drift or source/test/checker change is fatal.

## The MIR behind owned-local views (#53)

Unoptimized builds also compile the binary crate through a small rustc wrapper (`RUSTC_WORKSPACE_WRAPPER`). It is written into Peeky's own build directory, and its bytes are rechecked before every command. For that crate only, the wrapper adds:
- `-Zmir-opt-level=0`;
- a `PreCodegen` MIR dump into `target/peeky-mir`;
- legacy symbol mangling.

`RUSTC_BOOTSTRAP` is set to that crate's name only, so no other crate gets unstable features. The test target and anything else Cargo compiles get no flags, and Cargo reuses the one binary unit for both commands. The dumps are a hashed build artifact.

`rust_mir` uses them as follows:
- It parses the dumps and runs a definite-initialization dataflow over each body.
- It maps the stop line to MIR blocks through the LLVM IR's debug locations, which already attribute macro-expanded code to the invoking line.
- It reads an owned `Vec<T>` (`T` an integer type, `bool`, `f32`, `f64` or `char`) or `String` local only if, in every such block (and any block codegen merged into it), the local is initialized at each place code of that line can be: before each statement on the line, or from another file (external macro code), following moves, drops and assignments statement by statement. A block whose code of the line no statement explains must keep the local throughout. The stop must be in the function's own file, and the MIR body must be identified positively: exactly one same-named body with a span on the function's `fn` line, owning every line of its code that any body has a span on.

Anything not understood proves nothing: an unparsed statement, a coroutine, a projected or doubly bound name, a body that is ambiguous for its IR function (macro-generated twins included), a block of unknown origin, or a stop in another file (a macro defined there). A crate using `#[collapse_debuginfo]` gets the whole-block rule only. Optimized builds use no wrapper and read no owned locals. Unsafe code that duplicates ownership (`ptr::read`) is outside the proof.

## Required deterministic proof

```sh
PEEKY_RUST_CARGO="$(rustup which --toolchain 1.96.0 cargo)" \
PEEKY_RUST_RUSTC="$(rustup which --toolchain 1.96.0 rustc)" \
PEEKY_RUST_DAP="$(xcrun --find lldb-dap)" \
PEEKY_RUST_DWARFDUMP=/usr/bin/dwarfdump \
PEEKY_RUST_LINKER=/usr/bin/clang \
PEEKY_RUST_DSYMUTIL=/usr/bin/dsymutil \
pytest tests/rust
```

On Linux, use the LLVM 18 paths from the Rust CI lane and omit `PEEKY_RUST_DSYMUTIL`. The main regression invokes the real `peeky-agent --rust-config` entry point with a deterministic decision provider and a real HTTP worker. It spawns no model. The observed sequence is:

1. Pause at the observation line: `start = 3`, `some = Some(3)`, `none = None`.
2. Change the live `i32` to `0`; continuation prints `PAGE:[10, 20, 30]` without a rebuild.
3. Propose invalid Rust syntax; the compiler error returns as a retryable `build` result.
4. Propose `start = 0`. The **Cargo test passes** (it only checks page 1), but the independent checker rejects later pages, so the candidate fails.
5. Propose `(request.page - 1) * request.page_size`. The compiled test and all checker cases pass on a fresh build.

The report keeps the original source, test, manifest, lockfile and checker unchanged. It records the candidate hash, build manifest, test executable hash, libtest summary and checker completion. Temporary workspaces are removed (`artifacts_retained: false`). A second regression changes the frozen test file mid-investigation, and verification fails fatally without accepting a fix.

Local macOS run (Apple LLVM 21, Rust 1.96.0): the full investigation took 5.05 s, and the frozen-test drift regression took 2.34 s. Linux timings are recorded in TESTING.md from the hosted lane.

## Reading Rust values

Rust reference parameters (`&[T]`, `&str`, `&Vec<T>`, `&String`, shared or `&mut`, where `T` is any integer type, `bool`, `f32`, `f64` or `char`) are read from the program's memory, at offsets checked against the build's debug information, when the debugger supports `readMemory` (lldb-dap from LLVM 20). Rows show `[memory]`; selectors index them (`values[0]`, `values[-1]`) and read their length (`values.length` for slices and `&str`, `list.len` and `list.capacity` through `&Vec`/`&String`). Text is shown whole. `&mut` parameters are read only in the innermost frame. Elements show as Rust's `{:?}` prints them (`[0.1, -0.0, 1e16, NaN]`, `[true, false]`), and each element row carries its exact type (`u64`, not LLDB's `unsigned long`). Scalars do too, with LLDB's name in `debugger_type`. Locals and parameters take theirs from the build's MIR (`usize`, `f64`, `char`). A field takes the one primitive LLDB's name can be (`double` is `f64`); only `long` and `unsigned long` (i64/isize, u64/usize) keep LLDB's name there. `f64`/`f32` values print as Rust's `{:?}` (`10.0`), and `u8`/`i8` values as integers (`65`, not LLDB's `'A'`). Owned `Vec<T>`/`String` locals are read too, in the innermost frame, where the build's MIR proves them initialized at the stop line. Where they may be moved, dropped or not yet assigned (`drop(v)`, `consume(v)`, `let s = s + "x"`, a `let label: String;` before its assignment, a move on that very line), they keep their raw fields (`ordered.len`) with a note, because their pointer can reach freed memory (#53). Elements may also be tuples, or structs your crate defines, whose fields are all such scalars (`Vec<(char, usize)>`, `&[Interval]`, `Vec<Point>` for `struct Point(i32, u8)`, generic ones like `Pair<u16>`). The build's debug information must show plain fields at aligned offsets (no enums, references, nested containers or `#[repr(packed)]`), and the compiler's own type picks the layout, because LLDB's names can collide (it names `Pair<i8>` `Pair<char>`). They print as a derived `Debug` would (`('a', 3)`, `Interval { start: 1, end: 10, open: false }`, `Point(1, 2)`, `(7,)`), even for a type with its own `Debug`. Fields are selectable, named as LLDB names them (`runs[0].__0`, `spans[-1].open`, `points[1].__1`), with their Rust types, and are read-only. Structs from the standard library (`Range<usize>`, which prints as `1..5`) and structs with other fields (a `String`) keep LLDB's summary, with a note. Two structs that share a path (one declared in a function's body, one in a module of the same name) cannot be told apart by name, so a container of either is opaque. A tuple or struct local, or a reference parameter to one (`s: Span`, `t: (i64, char)`, `last: &Span`, `p: Point`, `m: Marker`), whose fields are all such scalars is previewed the same way (#106): `inspect`, `get` and probe rows show `Span { start: 2, end: 3 }`, `Point(1, 2)`, `(7,)` or `Marker` with `[memory]`, read from memory at the offsets the build's debug information gives, and its fields stay selectable (`s.start`, `t.__1`) with their Rust types. The proofs are the containers': an owned local (or a by-value parameter) only where the build's MIR proves it initialized at the stop line, in the innermost frame; a reference parameter once the IR proves it live, a `&mut` one only in the innermost frame. LLDB's own value and fields stay for a local that may be moved, dropped or not yet assigned (`[stale]`, #108), a caller frame's local, a reference local, a nested struct (`Rect { a: Span, .. }`), a packed one, one with any other field (an enum, a reference, a `String`), one sharing its path with another struct (a function's own `Token`), and the standard library's (`Range`). The compiler's own type picks the layout (`Pair<i8>`, which LLDB names `Pair<char>`), and LLDB's name must spell it (`Pair<char32_t>` is never a `Pair<i8>`). In a generic function, its closures and its impl's methods, a type the MIR declares that names a type parameter is never taken for the frame's, whatever the parameter's name (`fn show<i8>(p: Pair<i8>)` may be called with chars): such a local or `Vec` stays raw, and a scalar keeps LLDB's type name; a reference parameter still previews, by the instantiation's own type. A const parameter is a value, never a type, so a function generic only over consts (`fn sum<const N: usize>`, `fn ch<const C: char>`) keeps its previews and Rust types. A packed struct (`#[repr(packed)]`) never previews, even where its fields fall aligned, and the DWARF of `struct Num { __0: u32 }` is that of `struct Num(u32)`, so no tuple struct previews (or reads in a container) in a crate whose sources have an identifier `__0` or enable a nightly feature (`#![feature(…)]`, also inside `cfg_attr`; Peeky's builds allow them, and `${concat(__, "0")}` declares `__0` with no such token). On stable Rust a crate cannot otherwise declare one: `macro_rules!` cannot join identifiers, and a procedural macro needs a crate Peeky's builds refuse (a dependency, library target or build script); every file the build reads is a declared input, and all are scanned (`Cargo.toml` and `Cargo.lock` too, which `include!` can read as Rust, as plain text). Optimized builds and debuggers without `readMemory` show no previews, nor does a preview longer than 1000 characters. A `Box<T>` local or parameter (or an array of them) shows its contents (`b.x`) under the same proof; where it may be moved or dropped it shows only its pointer, `[unproven]`, with a note, because the allocation may be freed and reused (#101). So does a Box a closure captures, and a pointer the MIR cannot vouch for: a generic `T`, `Self` or `impl Trait` value, an `async fn`'s parameter (its future holds it twice), or an unmangled (`#[no_mangle]`) function's (these are never proven). Of a name bound more than once, only the bindings in scope at the stop count. In the innermost frame of an unoptimized build, a reference (also `&str`, or a tuple, `Vec` or closure holding one) reads while the code still uses it (the borrow checker then keeps its target), or after its last use while no call or drop has run since (only arithmetic, copies and branches). Past a call or drop after its last use, what it pointed into may be moved, dropped or reallocated, so it shows only its pointer too (#110): probe a line that still uses it. A line breakpoint stops where its line starts in each lexical block (Peeky tells which from the stop's column and the build's LLVM IR), so a reference reads on the line of its last use; a step or a pause can stop inside a line, after a call there. A macro that declares variables of its own (`println!`, `assert_eq!`) adds a stop in each of its lexical blocks, all at the macro's column. Peeky tells them apart by the lexical block the stop's address is in (the build's DWARF, matched to the MIR's scopes and the LLVM IR's blocks by the names each declares, #115): a reference not used later reads at the stops before the macro's first call, and shows only its address at those after it. Where the address does not tell the block apart (a block whose code the compiler left out, an `.await`'s, two blocks declaring the same names on one line, the function's own line, an `#[inline(always)]` or caller frame), every stop of the line is judged as any of them. A raw pointer (also `NonNull`, `AtomicPtr`) keeps no borrow and always shows only its address (one inside a tuple reads with the tuple, as one in a struct does). Always read: a reference into what a shared reference parameter points at (`&items[0]`: the caller's borrow freezes it), one at a variable of an enclosing scope that is initialized at the stop (`&p`), a parameter never reassigned that holds references (`&mut self`, `p: &mut Pt`, `v: View<'_>`, `(&Pt, i64)`: the caller lent them for the call), a literal (`let s = "text"`) and a fn pointer, unless written through a `&mut` to it. Between the drop and the store of `*v = new` (a stop inside the old value's `Drop`, then `step --out`), `v` shows only its address, also when the store goes through a reborrow, a struct, `Cell` or closure holding it (`Ctx { v: &mut *v }`), a call returning it (`id_mut(v)`), or a closure's capture of it; and a Box partly moved out of (`let d = bx.data;`, also `bx.inner.data` of a Box in a Box) shows only its pointer. A stop inside a macro from another file, at a line the build's IR does not explain, in a function too big or unusual to analyze (its dataflow past its budget), or in methods a macro generates (which the MIR cannot tell apart) gates every borrowing local; a reference parameter never reassigned still reads, unless the function drops what it points at (`*h = new`, `*c.borrow_mut() = new` through a shared `&RefCell`). In a crate using `#[collapse_debuginfo]` a line invoking a macro is judged whole. A frame of an `#[inline(always)]` function (LLVM inlines it even at opt-level 0, so no IR of its own places the stop) is judged at every statement of the stop line and after each of its calls; one whose code cannot be told apart from another's (methods a macro generates) gates every borrowing local, except a reference parameter as above. Async bodies (an `async fn`'s, an async block's or async closure's) are judged as functions are: a local the future keeps across an `.await` reads while used ahead, and one it does not keep shows only its pointer after the `.await`, where a later poll's frame holds whatever it held (#116). An `async fn`'s parameter shows twice, as the future's field and as the poll's copy; both read where they hold the same pointer (for a slice or `&str` parameter, only where the debugger reads memory: lldb-dap from LLVM 20). Lines with an `.await` hide more than the same code without `async`: the `.await`'s column is also where the awaited future is dropped if a panic unwinds, and a reference handed to the awaited future is past its last use while it is polled. In a 140-line async program, 145 of 899 reference rows (up to four stops of every line) were hidden, 103 of them on lines that hide them in its synchronous twin too. A local that may own memory through a pointer inside it (a struct, tuple, array or enum holding a Box, Vec, String or Rc; any struct counts, since the MIR names no fields, but not a tuple or array of only primitives and references, unless a generic function's type parameter has a primitive's name) is judged by the same proof (#108). Where the build's MIR does not prove it initialized at the stop, in the innermost frame of an unoptimized build (after `drop(h)`, `consume(h)`, `let g = h;` or a partial move `let d = h.b;`, and wherever nothing is proven: an optimized build, a closure's or async block's capture, a macro's twin functions), it is `[stale]`: its fields show the bytes left in its own storage, the moved-from copy, each `[stale]` with a note (`h.n`, `h.v.len`), and every pointer inside it (a Box field, a `Box<str>`, a reference, an Rc) shows only its address, `[unproven]`, so `h.b.x` is refused and `session get h` lists `h.b` as not expandable. In a caller frame (`--frame N`) its fields read unmarked where the MIR proves it initialized on the call's line (lent as `&mut h`), and its pointers still show only their address, as a callee may be midway through replacing a Box it was lent; where the call may move it (`consume(h)`) it is `[stale]`. A field or element reassigned in place (`h.b = Box::new(..)`, `w.s = String::from(..)`, `arr[i] = ..`) drops the old value and stores the new one, which leaves the local whole if it was whole before; a field moved out and then stored again (`let d = h.b; h.b = ..`) still leaves it `[stale]`. A data-carrying enum other than `Option<i32>` stays opaque. Optimized builds prove nothing, so there every Box, and every pointer the MIR cannot vouch for, shows only its pointer (#111). Reference locals (`let view: &[i32]`) keep their raw fields. Optimized builds give no proof, so parameters there keep their raw fields or show as optimized out. Long values show their first elements or characters with `(first k of N)`; up to 256 elements stay selectable.

## Changing fields and elements (#105)

`--set` (and `session set`) also changes an integer field or element of a struct, tuple or array local: `s.end=10`, `o.span.start=1`, `o.marks[1]=2`, `t.__0=3` (LLDB's name for a tuple's `.0`), `arr[2]=4` (an element of an array of any length, fetched alone at any step of the path), and of a shadowed local LLDB names with where it is declared (`s @ main.rs:81.a`, as after `let mut w = w;`; an integer one too: `x @ main.rs:18=500`). What a change makes true: the value's storage holds the new value, and the program's later reads of it see it. Only where that holds:
- the frame is the innermost one, and the build is unoptimized (opt-level 0);
- the root local is one the build's IR keeps in memory (as for integer locals) and its MIR proves initialized at the stop, so not moved, dropped or yet to be assigned (`drop(h)`, `let later: Span;` before its assignment): a change there would be lost, or overwritten by the assignment;
- the path, read from the build's debug information rather than LLDB's type names, selects only fields of structs and tuples your crate defines and elements of fixed-size arrays: nothing through a reference, a raw pointer or a `Box` (what one points at may be moved or freed, #101), and nothing inside an enum (variants and niches), a union, a `#[repr(packed)]` struct (its fields may be misaligned) or a standard-library type (`Vec`, `String`, `Range`, `Option`);
- the value is an `i16` to `i64`, `u16` to `u64`, `isize` or `usize` (not `bool`, `char`, floats or 8-bit integers), and the new value is in its range.
- no statement under way at the stop has already read the local (#105 review): the stop is a line breakpoint, or a step that ends at its line's lowest address in the function (where a breakpoint on it stops), and from the line's first code in the stop's lexical block the build's MIR shows no temporary that may hold a value read from it (a copy of it or of a field, a read through a pointer that may point into it, or what a call given such a pointer returns, other than `format_args!`'s, which keep the pointer, unless the crate itself names something `core` or `std` that could pass for them) used again. A breakpoint's place on its line is told by the stop's column (the line's first MIR place may emit no code, as `&k` in `let t = (&k,` / `s.a,` / `s.b);`): with no column, the change is refused. Every other stop is refused (`cannot be changed here`), for an integer local too: a step back from a call (`step --out` into `let t = s.a + f();`), a step back onto a statement's first line after its later lines ran (`let arr = [s.a,` / `k,` / `s.b];` builds its array on line 1, after reading `s.a`), and anything else no breakpoint or step explains. A breakpoint on `+ f();` under `let t = s.a` is refused by the MIR (past the read), as is anything the MIR does not explain.

The change is made with the debugger's `setVariable` on the field, then the frame's scopes are listed again and the field read back: it must be the value asked, or the change is reported as not made (`MUTATION_REJECTED`), or, when something else was stored, the session is closed. A struct or tuple local shown as a preview read from memory (#106: `Span { start: 1, end: 2 } [memory]`) is its own storage, so its fields change the same way, under the same rules: the write goes through the debugger's own variable (not the preview), and the preview is read again afterwards, which must show the new value too (else the session is closed). What a container holds (a `Vec`'s or `String`'s contents, a `Box`'s target) and an enum's variant stay unchangeable (`inside a value Peeky decodes itself`). A caller's frame is never changed: a call it is making may hold a copy of the old value. Copies the program made itself keep the old value (`let a = s.a;` above the stop, a `for` loop's iterator over `0..s.n`), and the stop's own line may overwrite the change (`s = Tri { a: 9, ..s };`). Fields carry no `[settable]` mark; a refused `--set` says which rule it broke (`` `pk` is a packed struct (Packed): its fields may be misaligned ``).

## Limits

One dependency-free binary and at most one integration-test target, edition 2021 or 2024. A plain `cargo new` crate qualifies: targets may be explicit (`[[bin]]`, `[[test]]`, discovery switched off) or Cargo's defaults (`src/main.rs`, `tests/*.rs`), provided nothing else Cargo would discover exists (`src/lib.rs`, `src/bin`, `build.rs`, test directories). `[dependencies]` tables must be empty, and package metadata fields (`description`, `license`, ...) are allowed. Without an integration test, `verify` relies on the checker alone. Edition 2024 was qualified by running the whole Rust suite (56 tests, every owned-local proof included) with its example crate switched to 2024. No workspaces, build scripts, dependencies, doctests or unit-test harness of the binary itself. libtest output beyond the 16,000-byte capture is a failure, not a pass. Test processes share OS permissions with the checker and are trusted code. No live-model Rust evaluation has been recorded.
